WHAT MOVED IT

Profiling the width-16 step found the GPU busy only 121 ms of a 1288 ms
decode. The cost was not arithmetic and not transfer -- it was the sheer
number of sequential tiny ops, roughly 0.25 us of latency each even
inside a captured CUDA graph. Cross-attention ran once per item, so the
graph grew with the wave:

  width 1     639 nodes
  width 16   4649 nodes

Batching it puts every item's cross K/V in one arena padded to the wave's
widest text, with an additive mask that is zero inside a chunk's own
length and -inf past it. One batched matmul replaces one attention per
item, and the graph stops growing:

  width 16    617 nodes   (was 4649)

Step 4.72 -> ~2.4 ms, and RTF 0.0229 -> 0.0176.

TWO BUGS FOUND, BOTH THE SAME SHAPE

The local transformer's composed CUDA graph captures the *device
pointers* of the hidden tensors it was built against. It has now bitten
three times:

  1. per-item hidden tensors      -> chunk 0 right, later chunks babble
  2. per-group wave_cond/uncond   -> group 1 emitted 167 s of audio for
                                     a 101 s script, because it had the
                                     same width as group 0 and so never
                                     invalidated
  3. width change between groups  -> composed at one width, replayed at
                                     another

The chain is now invalidated on a change of width *or* of either hidden
tensor's address, and given three eager passes to warm before recomposing
-- composing too early fails once and disables the chain for the run.

REMAINING FRUIT, RANKED

  1. Codec chunk width (--tts.chunk-frames 3 -> 32) is worth RTF 0.0176
     -> ~0.0102 on its own. Pre-existing knob, applies to stock main too,
     and costs byte-reproducibility (-49 dB SNR). A deployment choice
     rather than a patch.
  2. The ~290 ms of per-group step-0 work, 29% of the producer thread.
     Twenty chunks each open through the single-item decoder path, and
     each one's opening hidden state is gathered into the wave pair by a
     host round trip. Batching the opening prefill would recover most of
     it.
  3. Encoder at 93 ms, of which about 20% is the overlapping history
     windows that get encoded and then overwritten -- a pre-existing
     waste, unchanged by any of this.

  Nothing else in the decoder looks cheap: the wave step is 2.43 ms for
  16 items, or 0.15 ms per item against 1.55 ms sequential.
